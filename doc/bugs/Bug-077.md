# Bug-077 · 加密知识库每次打开（无编辑）全部 _meta.json 被重写：首读密钥缓存竞态

> [返回 Bug 索引](../历史Bug记录.md) ｜ 状态：已修复（测试完成）

- **ID**: Bug-077
- **日期**: 2026-10-15
- **现象**: Bug-076 修复后，用户通过 start-desktop.bat（源码版）打开**加密知识库** dfzx、不做任何编辑，关闭后 6 个含笔记目录的 `_meta.json` 每次都被重写；字段级 diff 显示除 updatedAt 外内容完全一致。百度同步盘因此每次打开都产生上传。
- **复现地点**: `second-brain/main.js` 的三个解密读函数 `vaultReadTextByRoot` / `vaultReadTextSync` / `vaultReadText`。
- **关联**: ED-33/ED-35 元数据增量改造、Bug-076（recent.json 无条件写）。
- **原因**:
  1. 三个函数的取值顺序错误：先 `const ring = encKeyCache.get(rootKey)`（进程启动后该库**首次**调用时缓存尚未建立，得到 undefined），其后 `encLoadList(root, ensureNoteKey(root))` 才通过副作用把 keyring 填进缓存——但局部变量 `ring` 仍是 undefined。
  2. `decryptNoteTextAny(raw, undefined, kid)` 对空 ring 的策略是**静默原样返回** `ENC1:` 密文（设计上防崩溃），于是该库本次进程的第一个加密笔记读取拿到密文：fh 指纹、字数、链接全部按密文计算。
  3. 启动时存在两条并发读取路径：`vault:get` 触发的全库重建（100ms 去抖）与渲染端恢复标签页的 `notes:read`。谁先成为"首读"取决于竞速时序：渲染端先读则密钥缓存提前建好、重建全读明文（零写入，如 11:20）；重建先跑则扫描前若干篇读到密文（密文指纹），且**每轮竞速边界不同 → 签名每轮都变 → diffWrite 每轮都判定变化 → 全量重写**（12:18、12:22 等）。
  4. 排查干扰项：11:42 的写入另有其因——用户同时使用了 10-10 的旧安装包（app.asar 无 meta-vault/writeIfChanged），旧包全量重写并丢掉 fh 等新字段，造成新旧版本 ping-pong；已确认 start-desktop.bat 跑的是源码 `node_modules\electron`。
- **状态**: 已修复（测试完成）
- **处理方法**:
  1. 三个解密读函数统一改为**先 `ensureNoteKey(root)` 建立/复用 keyring 缓存，再 `encKeyCache.get` 取 ring**（ensureNoteKey 幂等，内部已有缓存短路），保证任何时序下首读都能解密。
  2. 不改动 `decryptNoteTextAny` 的空 ring 防崩溃语义（调用方契约由调用侧保证）。
- **验证结果**:
  - `npm test` 286 通过、0 失败（新增 Bug-077 防回退断言 3 组：三个函数体内 ensureNoteKey 必须出现在 encKeyCache.get 之前）。
  - 真机 dfzx 加密库经 start-desktop.bat 连续开关两轮：第一轮 6 个镜像各写一次（修复历史竞速污染的密文指纹，收敛到明文记录）；**第二轮 hash+mtime 全部零变化**；recent.json 两轮均未重写。
  - 笔记本体在开关库过程中零改动（排除 stripMetaId/重加密干扰）。
- **防再犯要点**: 见 `doc/bugs/防再犯清单.md` CD-58。
