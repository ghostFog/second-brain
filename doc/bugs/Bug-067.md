# Bug-067 · 单篇笔记显示密文（旧密码 key 残留 + keyring 不一致，缺修复入口）

> [返回 Bug 索引](../历史Bug记录.md) ｜ 状态：已修复（待真机验证）

- **ID**: Bug-067
- **日期**: 2026-09-26
- **现象**: 打开某篇笔记时编辑器显示 `ENC1:` 密文原文（无法解密），切换其他笔记可正常打开；`.second-brain/vault-enc.json`（M3 keyring）与磁盘实际加密该文件的密钥不一致——该文件是用**旧密码派生出的 M2** 加密的，而当前 keyring 里只有新密码的 key（或列表条目 key 指向已不在 keyring 中的 keyId），读取链路 `decryptNoteTextAny` 遍历 keyring 全部失败返回密文原文。系统无任何「输入旧密码重新加密修复」入口，用户无法自助恢复。
- **复现地点**: `main.js`（`vaultReadText*` → `decryptNoteTextAny` 全失败返回密文、`encIsFileEncrypted`/`encLoadList` 列表判定）；`js/editor/editor-host.js`（`openNote` 读取内容直接渲染，未检测密文）；无修复 IPC。
- **原因**: ① 历史/中间态遗留——修改笔记密码（`encReencryptAll`）或全库加密过程中断、外部同步（非走 `encListAdd`/`encRebuildList` 路径）后，个别文件仍是旧 key 加密；② keyring（M3）只保留了新 key，旧 key 丢失或未并入，`decryptNoteTextAny` 按条目 key / 遍历 keyring 均解不开；③ 该文件在列表（`encIsFileEncrypted=true`）但 `vaultReadText` 解密失败时**原样返回密文**（现有兜底设计），渲染端又无密文检测与「输入旧密码修复」能力，用户只能看到密文。
- **状态**: 已修复（待真机验证）
- **处理方法**: 新增「单篇密文笔记输入旧密码修复」链路（异常处理，不动全库）——① `main.js` 新增 `encRepairNote(root, rel, pwd)`：用户单独输入密码 I1 → `deriveNoteKey` 派生 M2_test → `decryptNoteText` 试解该文件（GCM 校验失败=密码不对返回 `wrong`）；**解密成功则用当前主密钥 M2 重新加密落盘**、把 M2_test 并入 keyring（`.second-brain/vault-enc.json` M3 v:2 落盘，此后读取/取消加密/全库重加密可解）、并把列表条目 keyId 强制更新为当前主密钥指纹（`encListAdd` 对已在列表条目会跳过，故直接 `list.set` + `encWriteListCipherSync`）；② 新增 IPC `app:encRepairNote`（`{rel, pwd}` → `{ok, reason?, content?}`）；③ `preload.js` `enc.repairNote` 桥接；④ `index.html` 新增 `#enc-repair-screen` 遮罩（复用 `.enc-unlock-card` 样式，含输入框/修复按钮/关闭）；⑤ `js/app-vault.js` 新增 `initEncRepair`：绑定遮罩交互（事件只绑定一次），暴露 `window.SBEncRepair.tryRepair(path)`，修复成功清 `edOutdated` 缓存后重新 `openNote(path)`（磁盘已是当前主密钥加密，重读即明文）；⑥ `js/app-layout.js` 在 `initVaultEncUnlock` 处一并调用 `initEncRepair()`；⑦ `js/editor/editor-host.js` `openNote` 内容装载成功后检测 `c.startsWith('ENC1:')`（非项目模式）→ 调 `SBEncRepair.tryRepair(path)` 弹遮罩。**时序回归修复（锁屏未解锁后台提前弹修复框）**：锁屏尚未解锁时盐未定（`encAppPwdPlain=null`），固定盐解不开 M3 → 读取返回密文 → `openNote` 误判「旧密码密文需修复」提前弹 `#enc-repair-screen`（与锁屏遮罩叠层）。修复：⑦ 的检测改为**先查锁屏状态**（`nd.security.getState()` → `hasPwd && !unlocked` 则不弹，等待解锁）；`js/app-security.js` `doUnlock` 解锁成功后新增**重载当前笔记**（`edCurrent` 内容以 `ENC1:` 开头则 `reloadNote(edCurrent)`）——盐已定后自动解密显示明文，仍解不开（真旧密码加密）才由 openNote 检测在已解锁状态下弹修复框，满足「锁屏密码输入正确后才开始」。
- **验证结果**: `node --check main.js / preload.js / js/app-vault.js / js/app-layout.js / js/editor/editor-host.js / js/app-security.js` 语法通过；npm test 243 通过、0 失败；临时自测脚本 9 项断言全过（① 旧 key 加密文件、keyring 只有新 key 时读取返回密文复现 bug；② 错误密码修复返回 `wrong`；③ 旧密码修复返回明文；④ 落盘已用当前主 key 重加密（新 key 可解、旧 key 解不开）；⑤ keyring 并入旧 key；⑥ 列表条目 keyId=当前主 key 指纹；⑦ 修复后按 keyring+列表读取=明文；⑧ 非密文文件返回 `already` 不误伤）。自测脚本跑完已删。真机待验证：① 设锁屏密码的库启动 → 锁屏遮罩在层，后台**不再**提前弹任何密码框；输入锁屏密码解锁后 → 当前笔记若为密文自动重载（正常解密显示明文，仍解不开才弹修复框）；② 未设锁屏密码场景 → 打开密文笔记直接弹修复框，输入旧密码修复后显示明文、再次打开不再弹。
- **防再犯要点**: ① 读取链路解密失败**不得静默返回密文让用户看密文**——需在渲染端检测 `ENC1:` 前缀并给出「输入旧密码修复」入口（用户自助恢复，而非只能手动改文件）；② 修复类操作必须**用当前主密钥重加密落盘 + 更新列表条目 keyId + 并入 keyring** 三处一致（与 `encReencryptAll` 的口径一致），否则修完仍解不开或列表 key 又与磁盘不符；③ 任何「输入密码试解单个文件」的校验用 AES-GCM 认证失败（`decryptNoteText` 返回原文）判定密码错误，勿用其它弱校验。
